🏗️ Vault Integration Architecture

Comprehensive Guide to Integrating vault-agent + vault-config-operator + MCP Policy-Gate

Overview Systems Overlaps Integration Roadmap Outcomes

📊 Executive Summary

This guide presents a comprehensive architecture for integrating three complementary systems that manage HashiCorp Vault:

🤖 Vault-Agent

LLM-based operational agent for interactive troubleshooting, diagnostics, and real-time Vault cluster management via chat UI

⚙️ Vault-Config-Operator

Kubernetes operator for declarative infrastructure-as-code configuration management with GitOps integration

🛡️ MCP Policy-Gate

AI-SDLC governance layer providing policy-as-code enforcement for prompt safety, tool manifest control, and regression testing

The Core Problem

⚠️ Critical Issue: Both vault-agent and vault-config-operator can create/modify Vault configurations, but without coordination. This creates:
  • Conflicting writes (last write wins)
  • Lost configuration changes
  • No audit trail for manual edits
  • Scattered credentials across systems

The Solution: Complementary Model

✓ Proposed Architecture: Give each system a distinct responsibility:
  • Operator = Sole authority for declarative state (in git)
  • Agent = Observability + emergency response only (read-only)
  • Policy-Gate = Governance layer ensuring safety (gates PRs)

3️⃣ MCP Policy-Gate

What It Is

AI-SDLC governance layer with four policy gates for any LLM-based agent.

The Four Gates

🎯 Gate 1: Prompt Review

Checks agent prompts for jailbreak patterns, enforces required patterns (mask, risk assessment), enforces max length

📋 Gate 2: Tool Manifest

Flags unclassified tools, requires sign-off for high/critical risk changes, detects drift from baseline

🔍 Gate 3: MCP Server Vetting

Validates command allowlist, version pinning, domain allowlist, no plaintext secrets

✅ Gate 4: Eval Suite

Golden transcripts regression testing, blocking vs warning severities, prevents behavioral drift

Policy-as-Code Example

policies/prompt_policy.yaml:

forbidden_patterns:
  - pattern: "ignore (all|any|previous) instructions"
    reason: "Jailbreak prevention"
  - pattern: "disable (safety|guardrails)"
    reason: "Safety must not be disabled"

required_patterns:
  - pattern: "mask"
    reason: "Agent must mask sensitive values"
  - pattern: "risk"
    reason: "Agent must assess risk before acting"

max_length_chars: 4000

Direct Overlaps (Conflict Risk)

1️⃣ Vault Configuration Creation

Vault-Agent User chat: "Configure AWS auth" → LLM calls Vault API No audit trail, no version control
Operator AWSSecretEngineConfig CRD → controller writes Declarative, audited
Collision Both apply configs → last write wins → lost changes

2️⃣ Policy Management

Both can mutate /sys/policy/... in Vault. Agent via CLI, Operator via CRD.

3️⃣ Secret Creation (KV, Database)

Both can create database roles and other secrets without coordination.

4️⃣ Secret Rotation

Conflicting rotation triggers from agent and RandomSecret CRD.

What ONLY Vault-Agent Does

  • Diagnostics & troubleshooting: "Why is the cluster unhealthy?"
  • AZ-failure detection: Analyze failed zones, decide unseal strategy
  • Emergency seal/unseal: Cluster outage response
  • Interactive decision-making: User approves risk assessment
  • Real-time monitoring: Poll cluster health every 20 seconds

What ONLY Operator Does

  • Declarative state management: "All configs live in git CRDs"
  • Drift detection: Auto-repair manual changes every 10 hours
  • GitOps integration: Works with ArgoCD, Helm, Kustomize
  • Bulk provisioning: Apply 100+ CRDs in one commit
  • Multi-tenancy: Different namespaces have different Vault roles
  • Lifecycle management: Finalizers clean up on CRD deletion
  • Full audit trail: K8s etcd + git history

Four-Phase Implementation

Phase 1: Operator as Declarative Base

Migrate all configs to CRDs

Policies → Policy CRDs from policies/ repo

Auth engines → AuthEngineMount CRDs

Database roles → DatabaseSecretEngineRole CRDs

Store all CRDs in Git

Feature branch → PR → review → merge → operator auto-applies

Use Helm/Kustomize overlays

Multi-env management (dev/staging/prod)

Validate reconciliation

Confirm all resources reconcile successfully

Phase 2: Agent Becomes Read-Only + Observability

Disable write tools

Make run_vault_command() readonly (ACL policy enforces)

Add new tools

get_operator_crds() - read K8s CRD status

suggest_crd_patch() - propose YAML changes (no apply)

Update system prompt

"Link to operator CRD workflow" for config changes

Test thoroughly

Verify reads work, writes fail gracefully

Phase 3: Policy-Gate Extensions for Vault

Create Vault-specific policies

policies/vault_prompt_policy.yaml - agent anti-patterns

Add new MCP gates

vet_operator_policies() - validate policy security

vet_agent_vault_instructions() - check prompts for anti-patterns

Wire into CI

GitHub Actions gates PRs before merge

Create Vault-Agent profile

profiles/vault-agent.yaml in MCP

Phase 4: Governance & Documentation

Create runbooks

"How to fix Vault issues via operator CRDs"

"How to add a new policy" (policies/ → operator sync)

"Emergency seal/unseal approval workflow"

Update monitoring

Alert if operator drift detection fails

MCP policy-gate sign-off

Require sign-off for agent prompt changes

User training

Learn operator CRD workflow, git-first mindset
